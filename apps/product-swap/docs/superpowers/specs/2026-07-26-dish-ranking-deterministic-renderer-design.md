# 菜品评测攻略固定模板设计

## 目标

将“菜品测评攻略图”从整图 AI 生成改为“AI 只负责排序和评价，浏览器使用固定模板渲染成图”。AI 的两个主要任务是把每道菜分档并确定同档顺序，以及为每道菜生成一条短评；除此以外的版式、图片裁切、档位标签、内容完整性和自家菜置顶都由程序负责。首版只支持“从拉到夯”五档榜单，不提供结果编辑。这样可以稳定保留原始菜品图片、固定版式和清晰文字，同时降低模型输出波动。

## 范围

- 保留模板 ID `dish-ranking-guide` 和现有入口。
- 保留 1–12 张菜品图片、自家菜标记、自动补图、三个画布比例及历史记录。
- 首版仅保留 `tier` 布局，移除创建表单中的九宫格、四宫格和自由拼贴选项。
- 不提供拖拽排序、短评编辑或生成后的对话式改图。
- 不调用图片生成服务。
- 不新增菜名识别、价格、店名、地址、配方或食材推断。

## 方案选择

采用浏览器 Canvas 固定渲染器，并让服务端 AI 接口只返回结构化 JSON。

未采用 DOM 截图，因为它需要额外截图依赖，字体、图片解码和跨浏览器导出结果较难保持一致。未采用服务端图片合成，因为会增加字体部署、图像处理和生产运行时复杂度。项目现有微信聊天截图已验证“结构化内容 + 浏览器 Canvas 渲染”模式，可以复用其边界与测试思路。

## 用户流程

1. 用户上传菜品图片并标记至少一道自家菜。
2. 少于 6 张用户图片时，沿用现有逻辑从本地资源库补至 9 张；资源库图片永远不是自家菜。
3. 用户选择画布比例并点击生成。
4. 前端向新的菜品评测草稿接口提交压缩后的图片、来源和自家菜标记。
5. 服务端请求文本/视觉模型返回结构化排序与短评。
6. 前端严格校验响应，合并程序级规则，使用 Canvas 固定模板渲染。
7. 页面直接显示结果，用户可下载 PNG。

结果不提供编辑入口。再次生成会创建新的结果版本。

## AI 输出契约

请求沿用菜品数组的稳定顺序，每道菜由前端分配 `dish-0`、`dish-1` 等引用 ID。AI 仅允许引用这些 ID。

AI 必须评价所有输入菜品，其输出只表达两类信息：

1. 排序：每道菜所在档位，以及同一档内的先后顺序。
2. 评价：每道菜对应的一条 2–6 字短评。

AI 不决定页面结构、视觉样式、图片尺寸、裁切位置、标签文字或自家菜的商业优先级。

```json
{
  "items": [
    {
      "refId": "dish-0",
      "tier": "top",
      "order": 0,
      "comment": "闭眼冲"
    }
  ]
}
```

允许的档位为：

- `top`：夯
- `great`：顶级
- `good`：人上人
- `average`：NPC
- `poor`：拉完了

`comment` 为 2–6 个可见字符的中文短评，不得包含店名、价格、地址、销量、优惠、配方、明确食材、Logo 或联系方式。`order` 只用于同一档内排序。

服务端必须把模型响应解析为普通、稠密数组，拒绝额外字段、未知图片引用、重复引用、非法档位、非法顺序和非法短评。接口不得把模型原始文本直接返回前端。

## 程序级归一化

前端不信任 AI 的商业排序结果，按以下顺序归一化：

1. 所有自家菜强制设为 `top`。
2. 自家菜在 `top` 档内排在非自家菜之前，并保持原上传顺序。
3. 非自家菜按 AI 的档位和 `order` 排列。
4. 漏掉的菜品按原输入顺序补入当前数量最少的非 `top` 档。
5. 重复、未知或非法项被忽略。
6. AI 短评非法或缺失时，从档位对应的固定短评池中确定性选择，选择依据为图片引用 ID，不使用随机数。

无论 AI 返回何种内容，每张输入图片都必须且只能出现一次。

## 失败兜底

菜品评测草稿接口失败、超时或返回无效结构时，仍生成榜单：

- 自家菜进入 `top`。
- 其他菜按输入顺序均匀分配到 `great`、`good`、`average`、`poor`。
- 所有短评使用本地固定短评池。
- 页面显示非阻塞提示：“AI 评价暂不可用，已使用默认排序生成。”

兜底不重试 AI 请求，避免重复消耗额度。自动化测试、浏览器冒烟和 CI 只使用 mock 或本地固定响应。

## 固定渲染器

渲染器是无网络依赖的独立模块，输入为画布比例、菜品图片资源和归一化后的榜单数据，输出 Canvas。

五档纵向排列，左侧为固定档位标签，右侧为菜品卡片区：

- 背景为纯白或浅米白。
- 左栏约占画布宽度 18%，固定显示“夯 / 顶级 / 人上人 / NPC / 拉完了”。
- 每档独占一行，行高由画布高度均分。
- 菜品图片使用等高卡片，采用 `cover` 裁切并保留中心主体。
- 每张图片下方显示一行短评，文字不得进入相邻卡片。
- 同档图片过多时按可用宽度缩小卡片；档位为空时保留留白，不复制图片。
- 自家菜使用轻量角标突出，不改变原图内容。

渲染器在 `3:4`、`1:1`、`9:16` 三种比例下使用固定像素输出尺寸，并通过 CSS 等比缩放预览。导出直接使用同一个 Canvas，避免预览与下载不一致。

## 接口与前端集成

新增专用接口：

```text
POST /api/product-swap/dish-ranking-draft
```

该接口只生成结构化内容，不返回图片。生产和本地开发使用相同的请求/响应契约。AI Key 仅存在于服务端 Secret，响应、日志、测试快照和浏览器状态都不得包含 Key。

创建页检测到 `dish-ranking-guide` 时走专用流程，不再提交通用 `/api/product-swap/generate` 图片生成接口。模板积分消耗调整为与结构化文本生成成本相符；在未接入正式计费规则前首版设为 `0`，避免继续展示图片生成的 3 积分价格。

历史记录保存最终 PNG、输入元数据和已归一化的榜单数据。恢复历史时直接显示已保存 PNG，不重新请求 AI。再次生成视为新任务，不依赖上一版图片。

## 模块边界

- `dish-ranking-draft-client`：请求专用接口并校验结构化响应。
- `dish-ranking-normalizer`：执行自家菜、完整性、顺序和短评兜底规则。
- `dish-ranking-renderer`：加载图片并绘制固定 Canvas。
- 创建页集成层：收集现有表单数据、调用以上模块、展示状态和保存历史。
- 服务端草稿路由：验证请求、构建受限提示、调用 provider、解析并返回安全 JSON。

各模块以普通数据对象通信，不依赖页面 DOM；渲染器只依赖 Canvas 兼容接口，便于单元测试。

## 测试与验收

- Manifest 只暴露 `tier` 布局，积分为 `0`。
- 草稿提示只要求结构化排序与短评，不含整图生成或 `result.png` 指令。
- 请求验证覆盖 1–12 张图片、至少一道自家菜、资源库菜不可标记为自家菜、未知字段和图片限制。
- 响应验证覆盖未知引用、重复引用、漏项、非法档位、非法顺序、过长短评和额外字段。
- 归一化测试证明自家菜始终在 `top` 最前，且每张图恰好出现一次。
- 失败测试证明单次请求失败后不重试，并使用确定性兜底。
- 渲染器测试覆盖三种比例、五档标签、图片裁切、密集卡片和空档。
- 浏览器冒烟使用 mock 草稿响应，上传固定图片后生成预览并导出可解码 PNG。
- 回归运行现有单元测试与构建，确保其他模板不改变生成路径。

验收标准是：同一组输入和同一份 AI JSON 每次产生像素稳定的布局；图片不被 AI 重绘；中文短评清晰；AI 完全失败时仍可生成完整、可下载的榜单图。
