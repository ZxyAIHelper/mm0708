# 菜品测评攻略图设计

## 目标

在现有模板系统中新增“菜品测评攻略图”。用户批量上传菜品图，标记一到多道自家菜品，选择排布方式后生成攻略图。自家菜必须占据最高视觉权重；其他菜可随机排布。用户图片不足时，从内置商品资源库自动补足。

## 范围

- 新模板 ID：`dish-ranking-guide`
- 一次上传 1～12 张菜品图
- 至少标记 1 张自家菜品，允许多选
- 用户上传少于 6 张时，从资源库随机补到 9 张
- 排布方式：
  - `tier`：从拉到夯，默认；档位为“夯 / 顶级 / 人上人 / NPC / 拉完了”
  - `grid`：九宫格点评
  - `quad`：四宫格攻略
  - `collage`：自由拼贴
- 输出比例：`3:4`（默认）、`1:1`、`9:16`
- 支持“补充想法”、生成后的多轮修改和版本历史
- 首版资源库只读，通过仓库内清单维护，不建设管理后台

## 方案选择

采用通用 `dish-list` 字段扩展，而不是模板专用页面或十二组固定字段。模板清单继续负责声明表单，创建页继续按字段类型渲染。这样可以复用现有模板目录、校验、历史和生成链路，并为后续多商品模板保留通用能力。

## 前端交互

`dish-list` 渲染为批量上传区和菜品卡片列表：

- 支持多选文件和拖拽上传
- 显示上传数量 `X/12`
- 每张卡片包含预览、删除和“自家菜品”切换
- 显示自家菜数量
- 少于 6 张时提示提交后将自动补充的数量
- 图片处理期间禁止提交
- 超过 12 张时拒绝多余文件并显示明确错误
- 提交前校验至少有一张图片且至少一张被标记为自家菜

资源库素材在首次提交时自动获取并转换为压缩图片数据，用户无需管理。补充素材使用 `source: "library"`，永远不能成为自家菜。用户素材使用 `source: "user"`。

## 数据模型

模板字段：

```js
{
  key: 'dishes',
  type: 'dish-list',
  role: 'dish',
  label: '菜品图片',
  required: true,
  minItems: 1,
  maxItems: 12,
  minOwned: 1
}
```

生成请求：

```js
{
  templateId: 'dish-ranking-guide',
  dishes: [
    {
      image: 'data:image/webp;base64,...',
      owned: true,
      source: 'user'
    }
  ],
  layout: 'tier',
  aspectRatio: '3:4',
  requirements: ''
}
```

服务端只接受普通、稠密数组；每项只允许 `image`、`owned`、`source`。图片沿用现有 Data URL、格式、体积、尺寸和解码校验。总数不得超过 12，至少一项 `owned: true`，资源库项不得标记为自家菜。

## 自动补图

提交时若用户菜品少于 6 张，前端调用同源资源 API，随机获取足够素材补到 9 张。素材下载后转成 Data URL 并随生成请求提交，使现有独立生成 API 无需访问商品站点或远程 URL。

若资源 API 或单个素材下载失败，生成仍使用用户已上传的图片继续；页面显示非阻塞提示。用户上传达到 6 张时不补图。

修改上一版时复用首次提交的完整菜品数组，不重新随机补图，保证视觉内容稳定。

## 商品资源库

从用户提供的参考截图中裁出可独立使用的菜品区域，压缩为约 480px 的 WebP。资源清单保存：

- `id`
- `name`
- `tags`
- `width`
- `height`
- `url`

可辨认菜名时使用菜名；无法可靠辨认时使用 `菜品-001` 格式。标签只使用可从画面合理判断的宽泛分类，不猜测店名、价格或精确配方。

只读接口：

```text
GET /api/dish-assets?limit=9&tags=甜品,主食&random=true
```

返回：

```json
{
  "success": true,
  "items": [],
  "total": 0
}
```

`limit` 限制为 1～12；`tags` 为逗号分隔并采用“匹配任一标签”；`random=true` 打乱候选结果，其他值保持清单顺序。接口返回公开缓存头，不返回文件系统路径。

本地开发服务器实现相同路由。线上新增轻量 Cloudflare Worker 入口：资源 API 由 Worker 处理，其余请求交给静态资源绑定。

## 生成规则

生成提示词明确每张输入图的序号、自家标记、来源和布局：

- 自家菜保持主体外观，必须处于最高档位或最强视觉位置
- 资源库素材和其他用户菜品可随机排布
- `tier` 中自家菜全部进入“夯”，其余档位随机但保持版面均衡
- `grid` 使用九宫格短评
- `quad` 将多道菜合理分组到四个区域
- `collage` 使用大小错落的海报式拼贴
- 保持中文短标签清晰可读
- 不编造店名、价格、地址、销量或具体配方
- 只生成一张结果图

修改任务以上一版为编辑底图，保留未被用户明确要求修改的布局、菜品和文字。

## 历史与后台生成

后台生成消息升级为版本 3，允许 `dishes` 数组；版本 1、2 保持兼容。历史记录按 `dish-0`、`dish-1` 等角色保存图片，并在输入元数据中保存每项的 `owned` 和 `source`，恢复任务时重建菜品列表。

## 错误处理

- 没有菜品：提示上传菜品图片
- 没有自家菜：提示至少标记一道自家菜品
- 超过 12 张：拒绝超出部分
- 非法数组、未知属性、资源库项标记自家：返回 `INVALID_INPUT`
- 图片格式、尺寸、体积或解码失败：沿用现有图片错误码
- 资源 API 参数非法：返回 400 和稳定错误结构
- 自动补图失败：非阻塞，使用用户图片继续
